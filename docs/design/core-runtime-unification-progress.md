# Core runtime unification implementation log

Updated: 2026-10-08

References: [Main design](core-runtime-unification.md), [T0 audit](core-runtime-unification-audit.md).

This log supports handover during the migration. Public execution and all registered tests for the old evaluator have moved to Core, and the two old execution evaluator files have been deleted. Consumers have moved to the shared public carrier and session, and the separate old facade implementation has also been deleted. The proof that the entire transformation preserves semantics is still incomplete.

## First objective completion assessment (2026-10-01)

**Removing direct typed-source evaluation at runtime and unifying public execution paths through Core are complete.** The assessment point is `a3168382`. Registered tests verified deletion of the old evaluator, migration of all 18 groups of old execution tests, the shared opaque artifact/value/session/checkpoint, the data initial heap, explicit raw migration, owned snapshot/full prefix, and authentication of inputs, heaps, and closures. An independent read-only audit also found no specific unresolved item blocking the first objective.

The audit checked the public compiler dependency path, actual `IndexedSession.start/resume`, cached Core body, `Core.runStateful`, finite safety of host/Contract/Wire, and failure/suspension boundaries. The public SourceCompiler/Current paths do not depend on the old ClosedSource / RuntimeValue / LocalExpression evaluator. Small fragment evaluators for the old Syntax.Expr/Term remain in independent spec/proof modules; this assessment does not claim deletion of every source-syntax evaluator in the repository. As agreed, the comptime evaluator remains in the preparation phase.

**The second objective is ongoing.** The final main theorem connecting the entire compiler, call/lambda history, specialization/evidence, and the actual staging pass is incomplete.

In the progress response to the user on 2026-10-02, the second objective was estimated at **about 60% by amount of work**. This estimate reflected the growing collection of partial proofs for major expressions, statements, and loops and their connections to the actual compiler; it was not a proportion of features, files, or tests. The remaining recursive calls, general lambda, evidence/coercion, specialization/staging, and integration of the overall main theorem are difficult, so this also does not mean the remaining time is 40%. Treat earlier percentages as history and prioritize the current status table.

In the progress response to the user on 2026-10-04, the second objective was estimated at about 65% by amount of work. This reflects recent dictionary connections, arbitrary-length tuple, preservation/reflection of lambda in the same model, and added staged primitive support. Given the remaining compound recursion, method/coercion, and final integration of all passes, this is not a proportion of required time.

In the progress response to the user on 2026-10-05, the second objective was estimated at about 70% by amount of work. This reflects semantic preservation and completion reflection for integer functions with staging, preservation of reference authority in the catalog, derivation of lambda permissions from actual compiler receipts, and connection of additional child expressions to the sole compiler induction. The first objective remains 100%, and the overall estimate with equal weighting is about 85%. The final main theorem connecting general functions, lambda, indirect calls, method, and all passes is incomplete; the percentages do not estimate remaining time.

## Public Core Entries and Scoped Control

`SourceCoreControl` treats only function trailing expressions as implicit return; expressions inside block/if use ordinary fallthrough. Cells allocated inside blocks/conditional branches remain in heaps, while continuation lexical scopes return to the outer scope. Early return/language failure suppresses subsequent outer statements.
`SourceCoreBasicEntry` completes canonical/evidence-plan validation and body Core checking at compile time. Runtime deeply validates arguments, lays out cells, and starts the same Core runner without evaluating source IR or recompiling.
`Result.typed` and `Checkpoint.typed` maintain safety of successful values, stores up to failures, and suspended states, exposing resumption laws. The public compiler retains observations in `ExecutionResult.coreLanguageResult` and supplies theorems projecting all finite-budget results to public source types.
The body retained by preparation is Core-typed, but proof of correspondence between its original typedBody/roots and "the body actually returned by this lowerer," and preservation of source meaning in input-cell layout, are not yet connected to entry proofs.

## Old Theorems That Type Safety Alone Cannot Preserve

- The old unconditional guarantees of `Core.well_typed_evaluates` and `Program.checked_*completes/*sufficient_fuel` do not hold. Current APIs explicitly require finite evaluation evidence.
- `LocalFunctionApplicationHasType.runtime_evaluates`, `ComputationReturnTreeElaborates.runtime_typed_execution`, and their wrappers likewise now explicitly require finite evaluation evidence. Typing of external closures alone does not imply termination.
- Making the environment reducible is insufficient for entire arbitrary expressions, because expressions can themselves allocate cycles of closure cells.
- Do not extend old `StoresRelated.eq_of_hasTypes` and exact-weakening lemmas to general runtime stores. Weakening changes generated-closure captures and breaks literal equality of final stores.
- Exact weakening for comparisons or similar work uses `LocalFragment.Basic` insertion lemmas or states explicit first-order restrictions on actual final stores. General evaluation uses relational store correspondence.

## Evaluation Order Established by the Audit

Compound assignment evaluates targets/indices, retains the leaf value before RHS evaluation, and uses that value for the operation.
Structural writeback uses the latest root incorporating RHS side effects.
Using the latest leaf for the operation or writing back the entire old root changes current meaning.

## Independent Semantics of Missing Defaults

After expression mapping indexes, missing-default fault rules were added for reads during place resolution and structural updates after the RHS.
They make successful index/default/member prefixes, key types, absent entries, and absence of defaults explicit, proving exclusivity with read / update success.
Read faults return the heap after evaluation of all index expressions; update faults return the latest heap after RHS evaluation.
Structural traversal precedes leaf modifiers, so missing-default is observed first even for invalid snapshot operands. Operand-fault rules also require successful reads of the latest root/path to preserve this order.
For BitNot, there is no intervening RHS, so it is proved that no new missing-default can arise in the same heap after successful target resolution.

Observations correspond to existing runtime `typeMismatch valueType none`. Runtime implementation and permitted mapping types are unchanged.
Other failures such as shape/type mismatch, out-of-range members, invalid root states, agreement with comptime type erasure, and general failure coverage/determinism remain.
Details and verification scope are recorded in the [audit material](core-runtime-unification-audit.md).
